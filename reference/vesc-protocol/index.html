WFB protocol notes

VESC transport, telemetry and configuration reference for WFB.

View source ↗

VESC communications reference for Wheelie app version 1.0.0.
Package com.thefloatlife.Wheelie
Version 1.0.0 (versionCode 6, iOS buildNumber 9)

Entries marked inferred describe unconfirmed encodings or behavior and require device verification before enabling writes. Later app or controller versions may change the protocol behavior documented here.

1. Package compatibility

The app expects a compatible custom package to be installed on the controller; it does not provide a .vescpkg or controller firmware installation path.

The app carries the custom-config schema described in §6. It can read and write that configuration without fetching the package, but refuses unsupported signatures with "Package Version Unsupported or failed to get config".

There is no supported Lisp source upload path. COMM_LISP_PRINT replies are explicitly discarded.

2. Transport — BLE

The GATT profile is the standard VESC one:

Constant UUID Role
VESC_SERVICE_UUID 6e400001-b5a3-f393-e0a9-e50e24dcca9e Nordic UART Service
VESC_CHARACTERISTICS_RX_UUID 6e400002-b5a3-f393-e0a9-e50e24dcca9e write, app -> board
VESC_CHARACTERISTICS_TX_UUID 6e400003-b5a3-f393-e0a9-e50e24dcca9e notify, board -> app

This is byte-for-byte the NUS profile that nrf51_vesc and VESC Express expose - no custom service, no renamed characteristics, no vendor base UUID. Any tool that speaks stock VESC BLE will connect. All of this app's customisation lives above the transport, inside COMM_CUSTOM_APP_DATA payloads.

After discoverAllServicesAndCharacteristicsForDevice the app walks servicesForDevice and pushes 'vesc' into a capability array if the NUS service is present; that tag gates binding the vescMessageHandler listener.

Device discovery filters on advertised name — helper bleDefaultNameIncludesWfb.

Write path — writeBuffer(deviceId, packet)

chunkSize = manager.mtu - 3
for each chunk:
    writeCharacteristicWithoutResponseForDevice(
        deviceId, VESC_SERVICE_UUID, VESC_CHARACTERISTICS_RX_UUID,
        chunk.toString('base64'))
await Promise.all(all chunk promises)

Note the chunks are issued concurrently and awaited together, not sequentially. Ordering depends on the platform BLE queue preserving submission order; on a stack that reorders, a multi-chunk packet would arrive scrambled.

Android permissions requested: BLUETOOTH, BLUETOOTH_ADMIN, BLUETOOTH_SCAN, BLUETOOTH_CONNECT, ACCESS_FINE_LOCATION, ACCESS_COARSE_LOCATION, FOREGROUND_SERVICE, FOREGROUND_SERVICE_CONNECTED_DEVICE, WAKE_LOCK. iOS declares the bluetooth-central background mode. There is a VescBackgroundService that keeps the connection alive under a foreground service.

3. Framing — generatePacket(payload, canId?)

Standard VESC serial framing:

short (len <= 256):   0x02  len:u8       payload  crc16:u16be  0x03
long  (len >  256):   0x03  len:u16be    payload  crc16:u16be  0x03

CAN forwarding is applied at frame-build time: if canId is supplied and payload[0] !== COMM_FORWARD_CAN, the two bytes [34, canId] are prepended. The send path (writeData) does the same automatically from _primaryCANDeviceId, so a caller normally doesn't pass canId explicitly.

CRC

CRC-16/CCITT (XMODEM), init 0x0000, table-driven, byte-at-a-time:

crc = table[((crc >> 8) ^ byte) & 0xFF] ^ (crc << 8)   // truncated to u16

Matches crc.c in vedderb/bldc.

Two framing bugs worth knowing about

  1. Off-by-one on the length-form boundary. The branch is len <= 256 for the short form; upstream uses len <= 255. A payload of exactly 256 bytes is emitted with a single length byte of 256 & 0xFF = 0, which the firmware will read as a zero-length packet. Payloads of exactly 256 bytes are therefore unusable.
  2. No 3-byte length form. Upstream supports start byte 0x04 with a 24-bit length for payloads > 65535. Not implemented here — irrelevant for the commands this app sends, but a limit if you're reusing the code.

VescBuffer

A reimplementation of VESC's buffer.c. Readers: readUInt8, readInt8, readUInt16, readInt16, readUInt32, readInt32, readDouble16(scale), readDouble32(scale), readFloat32, readDouble32Auto, readString, slice, size, raw. Writers mirror these, plus writeDouble32_Old retained for compatibility.

readDouble16(scale) / readDouble32(scale) are the scaled-integer forms (read a signed int, divide by scale). readDouble32Auto is the float32-packed-in-uint32 form.

⚠ Duplicate ID 100

The enum assigns COMM_GET_MCCONF_TEMP = 100 (upstream value is 91) while also assigning COMM_BMS_FORCE_BALANCE = 100. In a TypeScript numeric enum this compiles fine but the reverse map enum[100] resolves to whichever was declared last. Since IDs 92–99 and 101 all match upstream exactly, 91 is almost certainly what was intended and 100 is a typo. If you're interoperating, treat COMM_GET_MCCONF_TEMP as 91 on the wire and expect this app to send 100.

Two other observations:

  • COMM_GET_CUSTOM_CONFIG_XML (92) is defined but never sent — the app carries the config schema locally instead (§6).
  • A 14-element array of "movement-capable" commands is built from COMM_JUMP_TO_BOOTLOADER, COMM_SET_DUTY, COMM_SET_CURRENT, COMM_SET_CURRENT_BRAKE, COMM_SET_RPM, COMM_SET_POS, COMM_SET_HANDBRAKE, COMM_SET_DETECT, COMM_SET_SERVO_POS, COMM_REBOOT, COMM_ALIVE, COMM_FORWARD_CAN, COMM_SET_CHUCK_DATA, COMM_CUSTOM_APP_DATA — purpose not confirmed (inferred: a gating or keep-alive list).

Also defined: HW_TYPE_VESC = 0, HW_TYPE_VESC_BMS = 1, HW_TYPE_CUSTOM_MODULE = 2, and the full upstream FAULT_CODE_* set (including FAULT_CODE_FLASH_CORRUPTION, ..._APP_CFG, ..._MC_CFG).

7. Custom config — COMM_GET_CUSTOM_CONFIG / COMM_SET_CUSTOM_CONFIG

The custom-config interface uses the local parameter schema.

getFloatConf(buffer) reads:

u8   (discarded)
u32  signature

then looks the signature up in a version map. The map has exactly one entry, version 1 — so this build supports a single WFB config revision, and an unrecognised signature yields null, surfacing to the user as "Package Version Unsupported or failed to get config". The signature value itself is computed at runtime from the parameter table (VESC Tool-style hash). Its numeric value is not specified here and must be verified before writing configuration.

Per version the app holds three generated artefacts: configPropertyMetadata (the schema), a parser built by getParser(metadata), a serialiser built by getEncoder(metadata), and configPageLayout for the UI. This is exactly the code-gen output that VESC Tool produces from a package's config XML — embedded rather than fetched.

8. Client command scheduling

Outbound commands are matched to responses through command callbacks. While callbacks are outstanding in serial command mode, the sender backs off in 10 ms increments before writing the next command.
